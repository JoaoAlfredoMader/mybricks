# MyBricks Web

Front-end of **MyBricks**, a real-estate portfolio management platform: properties, clients, rental contracts and short-stay reservations, finances and portfolio KPIs (yield, cap rate, NOI, IRR).

> Portfolio project. API: [my-bricks-back-end](https://github.com/JoaoAlfredoMader/my-bricks-back-end).

## Stack

- **React 19** + **TypeScript** (strict) on **Vite**
- **TanStack Router** (file-based routes) and **TanStack Query**
- **Tailwind CSS 4** and **shadcn/ui** on **Base UI**
- **Better Auth** client (organization, admin and anonymous plugins)
- **openapi-fetch** with types generated from the back-end OpenAPI document
- **React Hook Form** + **Zod**
- **Vitest** + **Testing Library**
- **oxlint**

Not used: TanStack Table (the tables are plain, sorted and filtered by the API) and a map library. The charts are hand-drawn SVG (see *Finances*). There is no map yet because the API has nowhere to keep a property's coordinates: its address has `latitude` and `longitude`, always empty, and the create and update requests do not take them (the back-end README lists geocoding as not covered).

## Getting started

Node 22 or newer.

```bash
npm install
npm run dev        # http://localhost:5173
```

In development Vite proxies `/api` to `http://localhost:3000`, so the browser talks to one origin and the session cookie works as it will in production. Start the API from the back-end repository (`npm run db:up`, `npm run dev`; see its README).

## Project structure

```
src/
├── app/                 # query client and router factories
├── routes/              # TanStack Router file routes (one file per URL)
│   └── _authenticated/  # everything that needs a session
├── routeTree.gen.ts     # generated by the router plugin on dev/build; committed
├── features/<feature>/  # everything a feature needs: components, hooks, lib, styles
│   ├── landing/         # the public home page
│   ├── auth/            # session and organization queries, sign-in/up/guest/sign-out, login screen
│   ├── app-shell/       # the frame of the signed-in screens (sections, impersonation banner)
│   ├── dashboard/       # the portfolio indicators at /app
│   ├── properties/      # the property list, detail and form, photos, documents, financing
│   ├── contracts/       # rental and short-stay contracts: list, detail, forms, PDF
│   ├── reservations/    # short-stay bookings: list, detail, forms, cancel
│   ├── clients/         # the property owners and the agencies: lists, detail, forms
│   ├── finances/        # transactions (lançamentos): list, filters, forms
│   └── occupants/       # the tenant/guest fields, search and validation that contracts and reservations share
├── components/          # shared components (cards, filters, pagination, dialogs); ui/ is shadcn/ui (generated by its CLI), form/ the form fields
├── lib/
│   ├── api/             # typed API client and the generated schema.d.ts
│   ├── auth-client.ts   # Better Auth client
│   ├── format.ts        # cents → R$, fractions → %, YYYY-MM-DD → date
│   └── parse.ts         # what people type (1.234,56 · 14/05/2021) → what the API takes
└── test/                # Vitest setup, render helper and a fake API
```

- **Routes stay thin.** A route file declares the URL and renders a component from its feature.
- **Features own their logic.** Data access will live in each feature's query and mutation hooks; components do not call the API directly.
- **Business rules stay in the API.** The front-end formats what the API returns (money in cents, fractions as percentages) and never recalculates derived values.

## Landing page

The home page (`src/features/landing`) opens on a full-screen render of a residential building, in a day and a night version taken from the same camera. Switching to night reveals the night render from the sky down, then the lights come up and a few stars twinkle. The visitor's choice is remembered in `localStorage`; the first visit follows the system's color scheme. Motion is limited to the opening of the page and the switch between day and night, and it is turned off when the system asks for reduced motion.

To replace the renders (16:9, same size and framing, at least 2560 px wide, open sky above the roof for the title):

```bash
npm run hero:images -- path/to/day.png path/to/night.png
```

It writes `src/features/landing/assets/hero/<scene>-<width>.webp` in several widths (never upscaled) and a `manifest.json`; the page builds its `srcset` from them, so no code changes.

The landing has its own palette and typeface (Bricolage Grotesque), scoped to `.landing`; the app screens will get their own theme.

## API client

`src/lib/api/client.ts` exports `api`, an [openapi-fetch](https://openapi-ts.dev/openapi-fetch/) client typed by `schema.d.ts`, which `npm run api:types` generates from the back-end's `docs/openapi.json` (the back-end repository is expected next to this one). The generated file is committed, so a fresh clone builds without the back-end. `openapi-typescript` runs through `npx` because it still asks for TypeScript 5 as a peer.

`unwrap(api.GET(...))` returns the data or throws an `ApiError` carrying the API's `code`, `message` and, for validation errors, `fieldErrors` (`[{ path, message }]`).

## Authentication

Better Auth runs on the API under `/api/auth`; the client (`src/lib/auth-client.ts`) only signs in, signs up, signs out and stops an impersonation. **Who is signed in comes from `GET /api/me`** (`sessionQueryOptions` in `features/auth/api/session.ts`), the same answer the API uses for its own checks: user, active organization, member role and `impersonatedById`. The client never picks or sends an organization.

- **`/login`** has two tabs, *Entrar* and *Criar conta* (name, e-mail, password of 8+ characters), and *Entrar como convidado*, which asks the API for a guest with a demo workspace full of sample data. Fields are checked with Zod before the call; Better Auth's error codes are shown in Portuguese.
- **`/_authenticated`** is a pathless layout route: without a session it sends the visitor to `/login?redirect=<where they were>`, and after signing in they go back there (only paths inside the app are accepted). A signed-in visitor who opens `/login` goes straight to `/app`.
- **Impersonation.** While `impersonatedById` is set, an orange banner sits on top of every signed-in screen with *Voltar para minha conta*; the API refuses every `DELETE` meanwhile.
- **Signing out** clears the whole query cache, so nothing from the organization outlives the session.
- **The organization's name and demo flag** come from Better Auth's `organization/get-full-organization` (`activeOrganizationQueryOptions`), since `/api/me` only carries its id. A guest's dashboard says how long until the demo is deleted, from `demoExpiresAt`.

## App theme

The signed-in screens follow TypeUI's **Executive** design skill, from its public description (the full specification is behind a TypeUI account): an off-white page (`#f6f7f9`), crisp white cards with 16px corners, deep slate actions (`#1e293b`), pill-shaped buttons, single-line fields and navigation items, and four pale accents (`bg-pastel-lavender`, `-yellow`, `-cyan`, `-pink`) for the occasional highlighted block. The tokens live in `src/index.css`, as shadcn's CSS variables, so the login screen and every shadcn component pick them up. The landing keeps its own palette.

## Dashboard

`/app` reads `GET /api/kpis/portfolio` in the route loader and shows, without recalculating anything:

- **the portfolio value** as the headline figure (compact, `R$ 6,57 mi`), with the part that produces income;
- **annual revenue, NOI, gross yield and cap rate** as stat tiles;
- **the cash flow** of the portfolio, month by month, under them (the chart of the *Finances* section, see *Cash flow* there). The dashboard already leads with its own figures, so the chart comes without the three totals the Finanças page puts above it; its total is the last row of the table view. Its period (last 12 months, this year, last year) is the component's own state. It is left out while the portfolio has no property;
- **properties by status** as a thin segmented bar beside a list with each status's count and share (the bar has a hover readout; the list keeps every value reachable without it);
- **one row per property**, highest value first: status, value, revenue, NOI, yield, cap rate and IRR. A rate the API could not compute shows a dash, with the reason for a missing IRR read to screen readers and shown on hover.

Each property name links to its page.

## Properties

- **`/app/imoveis`** lists the portfolio by name (`GET /api/properties`, 20 per page): type and subtype, usage, the status the API derives, private area and estimated value. The name search (applied a moment after typing), the type and usage filters and the page live in the URL (`?search=&propertyType=&usageType=&page=`), so a filtered list can be shared or reloaded; a malformed value is ignored. While a new page loads, the previous one stays on screen, dimmed.
- **`/app/imoveis/$propertyId`** shows one property (`GET /api/properties/{id}`) with its own indicators (`GET /api/kpis/properties/{id}`): value, revenue and where it comes from, NOI, yield, cap rate and IRR. Below them come cards for characteristics, owner and management (the client's name from `GET /api/clients/{id}`), rent, acquisition, financing, documentation and notes. Cards with nothing to say are left out. A property outside the caller's scope answers 404 in the API and shows *Imóvel não encontrado*.
- Subtype names come from `GET /api/lookups/property-catalog`, loaded with the page and cached for the session.

- **`/app/imoveis/novo`** and **`/app/imoveis/$propertyId/editar`** share one form (`PropertyForm`), with *Novo imóvel* on the list and *Editar* on the property. Only the name, type and usage are required. The fields follow the API's rules before it is called: the usage and subtype menus offer only what fits the chosen type; the rent fields open only for usages that earn income and only when the rent is typed in (not taken from a contract); the financing fields open only for a purchase or a construction; an inheritance needs its base date; the address, once started, needs a city and a street. The city is searched in the API's IBGE list as you type.
- The form keeps what is typed as text and converts it only on submit (`src/lib/parse.ts`): `680.000,00` becomes 68000000 cents, `38,5` becomes 38.5 and `10/03/2022` becomes `2022-03-10`. Editing sends every field, with `null` for whatever was cleared, so turning the financing off removes it. Errors from the API land under their field when its path is known, with the rule translated to Portuguese; anything else shows at the top.
- After saving, the property page opens and the list, the dashboard and the indicators are refetched.

- **Photos** sit on the property page, cover first: *Adicionar fotos* sends several at once, one after the other in the order chosen (JPEG, PNG or WebP, up to 15 MB, 30 per property). Arrows move a photo, the star makes it the cover (`PUT …/photos/order` with the whole new order, shown at once and put back if the API refuses), and the bin removes it after a confirmation. Images load straight from `contentUrl`, authenticated by the session cookie.
- **Documents** are listed below the details: an optional category, then *Enviar documento* (PDF, image, DOCX or XLSX, up to 15 MB); each can have its category changed in place, be downloaded (the API always serves it as an attachment) or be removed after a confirmation.
- Files are checked here before they travel (type, size, emptiness), and the API's own refusals (`413`, `415`, the photo limit) are explained in Portuguese.
- **Excluir** removes the property with everything attached to it, after a dialog that says so. The page is left before the cache is cleared, so nothing tries to show the deleted property again.
- **While impersonating**, the delete buttons are not offered at all, since the API refuses every `DELETE` then.

- **Financing.** A financed property gets a full-width card with its terms (from the property itself, so they show even if the schedule fails) and the schedule from `GET /api/properties/{id}/financing-schedule`, as of the API's today: how many installments are paid (a thin bar with the count beside it), the outstanding balance, the next installment, what was paid so far and the interest over the whole contract. Below, the installments of one year at a time (amount, interest, amortization, balance after, and *Paga* / *Próxima* / *A vencer* in words), opening on the year of the next installment; arrows and a year menu move between years. Every figure comes from the API: an installment is shown as paid when its number is within `summary.paidInstallments`. The schedule is only asked for when there is a financing, and it is refetched with the property after an edit.

## Contracts

A contract ties a property to its occupant: a tenant with a monthly rent (*Locação*), or the operator of a short-stay property (*Temporada*, no fixed rent: income comes from reservations). Contracts are never deleted, only ended or cancelled.

- **`/app/contratos`** lists them newest start first (`GET /api/contracts`, 20 per page): occupant, property, type, term (`08/01/2026 a 07/01/2028`, or *Desde* for an open-ended one), monthly rent and status. Status, type and property filters and the page live in the URL (`?status=&contractType=&propertyId=&page=`).
- **`/app/contratos/$contractId`** shows the occupant (CPF/CNPJ and phone formatted), the term, the rent terms and the notes. While the contract is active it offers *Editar*, *Encerrar* (asks for the last day, today by default, checked against the start before the call) and *Cancelar contrato* (for a contract that never took effect, after a confirmation). A conventional contract can have its **PDF** generated from the organization's template (`POST …/pdf`) and downloaded; generating again replaces it.
- **`/app/contratos/novo`** creates one. The property menu offers only properties that can have contracts (not own use nor loan for use), and the type follows the property: a short-stay property gets a short-stay contract with no rent fields. If the property's rent is typed in on the property itself, the form says how to switch it to *Do contrato ativo* first; if the property already has an active contract, it says that one will be ended on save (the API does it in the same transaction). The occupant is either new (name, optional CPF/CNPJ, phone and e-mail; a CPF/CNPJ already on file reuses that occupant) or picked from those on file (`GET /api/occupants`, searched by name, document or e-mail). Opened from a property (`?propertyId=`), the form starts with it chosen.
- **`/app/contratos/$contractId/editar`** changes what the API lets change on an active contract: the end date (cleared for an open-ended one), the rent terms and the notes. An ended or cancelled contract sends the visitor back to its page.
- **The property page** lists the property's five latest contracts, with *Ver todos* and *Novo contrato*.
- After any change, contracts, properties (their status depends on the active contract) and every indicator are read again. The API's rules come back in Portuguese, under the field when the API names one.

### Contract template

**`/app/contratos/modelo`** (*Modelo do contrato*, from the contract list; *Editar o modelo* beside the PDF button on a contract) edits the text every conventional contract's PDF is made of (`GET`/`PUT`/`DELETE /api/contract-template`). There is one template per organization; until it saves its own, the API serves a plain residential lease (the page says it is not legal advice and has to be reviewed).

- **Three parts**, each a small visual editor with its own toolbar: *Cabeçalho* (the title, centered), *Cláusulas* (the body, required) and *Rodapé*. The toolbar offers the only markup the PDF understands: title, subtitle, text, bold, italic, underline, bullet and numbered lists. Pasting always brings plain text, so nothing foreign gets in.
- **Tokens.** *Marcadores* lists what the API says can be typed (`{{locador}}`, `{{locatario}}`, `{{valor_mensal}}`… with their descriptions); clicking one types it where the cursor is, in the part that was last focused. A token the catalog does not have is flagged as soon as it is typed, with the one it was probably meant for (`{{locadro}}` → `{{locador}}`), since the PDF prints it as written.
- **Preview.** *Prévia* shows the contract as a page with example data (a made-up landlord, tenant and property); an unknown token stays as typed, as in the PDF. The real PDF uses the data of the contract it is made for.
- **Saving.** The editor cleans the HTML the way the API does (allowed tags only, no attributes, scripts dropped, a `div` becomes a paragraph; `lib/template-html.ts`), checks that the clauses have text and the lengths (5,000 for the header and footer, 100,000 for the clauses), and sends the three parts. The save button is only on while something changed, *Descartar alterações* starts over from the saved text, and *Voltar ao padrão* (after a confirmation) deletes the organization's template. PDFs already generated do not change: a contract's PDF is generated again to use the new text.
- **Who.** Only owners and admins write the template (the API answers 403 to a member): a member sees the page read-only, with the preview. *Voltar ao padrão* is a `DELETE`, so it is not offered while impersonating.
- **How the editor works.** It is a `contenteditable` element driven by `document.execCommand`: deprecated on paper, but the one API every browser still ships for this. The element's text is only ever set once (`RichTextEditor` keeps the first `initialHtml`; the page starts it over with a new `key`), because rewriting it on each keystroke would send the cursor to the start. The tests stub `execCommand`, which jsdom lacks, so what they check is what the editor asks of it and what it sends, not how a browser lays the text out.


## Reservations

A reservation is a stay at a short-stay property (*usage: Temporada*). Like contracts, reservations are never deleted: a cancelled one stays on record and frees its nights.

- **`/app/reservas`** lists them by check-in, latest first (`GET /api/reservations`, 20 per page): guest, property, stay (`22/11/2026 a 27/11/2026`), nights, total and status. The status and property filters and the page live in the URL (`?status=&propertyId=&page=`); the property menu offers the short-stay properties.
- **`/app/reservas/$reservationId`** shows the guest, the stay (dates, nights as the API derives them, total), the linked contract if any and the notes. While the reservation is confirmed it offers *Editar* and *Cancelar reserva* (after a confirmation). A cancelled one is read-only.
- **`/app/reservas/nova`** creates one. Only short-stay properties are offered (with a pointer to the property form when there are none). The guest is new or picked from those on file, the same fields contracts use for their occupant (`features/occupants`). The total can be left blank (the API takes it as 0). If the property has active short-stay contracts, one can be linked; the stay must fit its term. Opened from a property (`?propertyId=`), the form starts with it chosen.
- **Overlaps.** Two confirmed reservations of a property cannot share a night, but a check-out can fall on the next check-in. When the API answers 409, the form says which stay is in the way, with its dates (taken from the answer's `details`), and scrolls the message into view.
- **`/app/reservas/$reservationId/editar`** changes the dates, the total, the linked contract and the notes of a confirmed reservation; the property and the guest are fixed. The total and the notes always go in the `PATCH`; the dates and the contract only when they changed, because the API checks them again whenever they are sent (a contract that ended since would otherwise block an edit of the notes). A contract already linked stays in the menu, marked with its status. A cancelled reservation sends the visitor back to its page.
- **The property page** of a short-stay property lists its five latest reservations, with *Ver todas* and *Nova reserva*.
- Cancelling is a `POST`, not a `DELETE`, so it works while impersonating.

### Calendar

**`/app/reservas/calendario`** shows the same stays as a month on a timeline: *Lista* and *Calendário* are two tabs of the section. A row per short-stay property (by name, linking to the property), a column per day, and each confirmed stay a bar that is a link to its reservation.

- **The bar runs from the middle of the check-in day to the middle of the check-out day.** A guest arrives during one and leaves during the other, so two stays that meet on a turnover day touch in the middle of it, a 2px hairline apart, and the check-out day is visibly still free for the next: the API's own rule (*the check-out day is free*). A stay that began before the month or goes on after it leaves its edge square and open. The geometry is `lib/calendar.ts`, apart from React, and tested on its own.
- **A guest's name is written in a bar only when it fits** (estimated from the name's length and the bar's width, never clipped); every bar carries the name, the dates and the nights in its accessible name, and hovering or focusing it opens the whole stay beside it: guest, property, dates, nights, total and whether a contract is linked. The readout is positioned from the bar and closes on scroll.
- **Columns share the room there is**, no narrower than 30px; below that the month scrolls inside its card, under the property names, which stay put. Weekends are tinted and today is marked in the header.
- **Month.** *Mês anterior* / *Próximo mês* and *Hoje*; the month is in the URL (`?month=2026-12`, left out for the current month, and a malformed one falls back to it).
- **Data.** One request per month, `GET /api/reservations?from=<first day>&to=<first day of the next month>&status=confirmed&pageSize=100`: the API's window `[from, to)` keeps the stays that overlap it, which is what a calendar needs. A cancelled stay frees its nights, so it does not show. A page is at most 100 stays; if the month has more, the page says so and points to the list (a month of a handful of short-stay properties is far from it).
- **No filters on the calendar:** it is the one view that shows every short-stay property side by side; the list has the filters.


## Clients and agencies

The *Clientes* item holds two lists, switched by tabs under the title: the **clients** (the owners of the properties) and the **agencies** (*imobiliárias*, which only have a name). Neither is the same as an occupant: a tenant or a guest comes with a contract or a reservation.

- **`/app/clientes`** lists clients by name (`GET /api/clients`, 20 per page): type of person, CPF or CNPJ, e-mail and WhatsApp, formatted. The name search (applied a moment after typing, `SearchInput`), the type filter and the page live in the URL (`?search=&personType=&page=`).
- **`/app/clientes/$clientId`** shows the data and the properties the client owns (`GET /api/properties?clientId=`, the first page, each one a link). The client's name on a property's page links back here. *Editar* and *Excluir* are in the header.
- **`/app/clientes/novo`** and **`…/$clientId/editar`** share one form (`ClientForm`). Only the name is required. The document follows the kind of person (*Pessoa física* → CPF, *Pessoa jurídica* → CNPJ, and the label changes with it); the form checks the number of digits and leaves the check digits to the API, whose refusal (*CPF inválido*) lands under the field in Portuguese. Editing sends every field, with `null` for what was cleared.
- **Deleting** asks first. A client that still owns properties is refused with a 409; the dialog says how many (taken from the answer's `details`) and that they have to be handed to another client or deleted first. While impersonating, the delete buttons are not offered (the API refuses every `DELETE`).
- **`/app/clientes/imobiliarias`** lists the agencies (`GET /api/agencies`, shared by everyone in the organization). Adding takes a name; renaming is done in the row; deleting asks first and is refused with the number of properties the agency still manages.
- After any change the client and agency lists, the menus of the property form and the properties (which show both names) are read again.

## Finances

*Finanças* is the list of **transactions** (*lançamentos*): revenues and expenses outside the routine of a property, such as a renovation, a building work, legal fees, an indemnity, the sale of the property or the financing installments. The categories come from the API (`GET /api/lookups/transaction-categories`) and decide whether a transaction is revenue or expense; the amount is always positive. Transactions feed each property's IRR. Fixed costs such as IPTU and condominium fees are the property's *despesas por ano*, which is what the yield, the cap rate and the NOI use; the page says so at the top.

- **`/app/financas`** lists them by date, latest first (`GET /api/transactions`, 20 per page): date, category and description, property, recurrence (*Avulso*, *Mensal até 25/03/2027*, *Mensal, sem data para acabar*), type and the amount with its sign. The filters are type, category (narrowed to the chosen type, in the API's order), property, one-off or recurring, and a period preset (*Este mês*, *Mês passado*, *Este ano*, *Últimos 12 meses*), all in the URL (`?type=&categoryId=&propertyId=&recurring=&period=&page=`, plus `?flow=` for the chart). The preset is turned into `from`/`to` on the viewer's calendar (`lib/period.ts`).
- **`/app/financas/novo`** records one: property, type (which narrows the category menu and drops a category of the other type), category, amount, date, description, and *Repete todo mês* with an optional *Repete até* (checked not to be before the first occurrence). Opened from a property (`?propertyId=`), it starts with that property and goes back to it.
- **`/app/financas/$transactionId/editar`** changes everything but the property, sending every field; turning the recurrence off sends `recurrenceEndsOn: null`, since the API refuses an end date on a one-off. *Excluir* sits next to the title (not offered while impersonating) and says that every occurrence of a recurring transaction goes with it.
- **The property page** lists the property's five latest transactions, with *Ver todos* and *Novo lançamento*.
- After any change the transactions and the indicators (the IRR) are read again.

### Cash flow

Above the list, *Fluxo de caixa* shows revenue and expenses month by month (`GET /api/kpis/cash-flow`), for the whole portfolio on the Finanças page and for one property on its own page (`?propertyId=`). The API does the adding: a recurring transaction is one record, so it is the API that spreads it over the months, and the screen only draws what comes back.

- **Chart.** Two columns per month (revenue in blue, expenses in orange, the first two slots of the categorical palette, validated with the `dataviz` script) and the result as a line in ink, all on one axis that always includes zero. A legend names the three series; the end of the line is labelled in the margin. Hovering or focusing a month (each has a focus stop and a spoken description) shows every series with what makes it up: rent, bookings and transactions on the revenue side, fixed expenses and transactions on the expense side. The geometry (the axis, the columns) lives in `lib/chart.ts`, apart from React, and is tested on its own.
- **Table.** *Ver como tabela* swaps the chart for the same figures month by month, with the totals: nothing in the chart is only readable by pointing or by colour.
- **Window.** *Últimos 12 meses*, *Este ano* or *Ano passado*, picked above the three figures and the chart that it scopes. On the Finanças page it is in the URL (`?flow=`, apart from the list's own filters); on a property's page it is the component's own state. While another window loads, the previous one stays on screen, dimmed.
- **What it is not.** It is the cash of each month: the rent in force that month (times the expected occupancy), bookings in the month of the check-in and transactions in the months they happen, minus the year's fixed expenses divided by 12. So the 12-month revenue is not the dashboard's *Receita anual*, which annualises today's rent; the page says so under the chart. In the portfolio view, own use and loan for use are left out, as in the dashboard, so the fixed expenses of 12 months equal the dashboard's annual expenses; asked for by property, they appear.
- **Dark mode.** The app has no dark theme yet (the `.dark` tokens in `index.css` are shadcn's grays), so the chart reads the app's tokens (`--chart-1`, `--chart-2`, `--foreground`, `--border`, `--card`) and will follow a dark theme once the tokens have one: its blue and orange would need their dark steps from the palette, validated again.

The transactions period filter (`from`/`to`) keeps a recurring transaction while its run touches the period, so a monthly installment that began in 2021 appears under *Este ano*.

Data colours follow the `dataviz` skill: the first four slots of its reference palette (blue, orange, aqua, yellow), validated on white with its script, always next to a text label. Money is formatted from integer cents and rates from fractions in `src/lib/format.ts`.

To try it locally, start the API (see the back-end README) and open <http://localhost:5173/login>.

```bash
npm test
```

Tests render the real route tree with a memory history (`src/test/render-route.tsx`). The router plugin is left out of the test config because the generated route tree is committed and the plugin's watcher keeps Vitest workers from starting.

Every test renders the whole app in jsdom, and a screen such as a property's page fetches a dozen things. With one worker per core the slowest tests starve and time out (the failures were different ones on every run, and each passed alone), so the config caps the suite at four workers and gives a test 15 seconds instead of five.

`src/test/fake-api.ts` stubs `fetch` with a small in-memory API: `/api/me`, the portfolio indicators, the active organization, the property list (searched, filtered and paged like the real one), each property, its indicators, its financing schedule, clients and agencies (listed, created, edited, deleted, with the 409 when they still have properties), contracts (listed, created with the replacement of an active one, edited, ended, cancelled, PDF), reservations (listed, created with the overlap check and its 409, edited, cancelled), transactions and their categories, and occupants answer from the fake state (`makeSession`, `makeKpis`, `makePropertyRecord`, `makeClient`, `makeContract`, `makeReservation`, `makeTransaction`, `makeFinancingSchedule`, a SAC schedule with round numbers), and each test adds the Better Auth endpoints it needs. Both clients look `fetch` up on every call so the stub takes effect, and jsdom runs on `http://mybricks.test` so a test can never reach the real API on `localhost:3000`.

Uploads are the one place tests do not go through the real request code: jsdom's `FormData` and `File` cannot be carried by Node's `Request`, so `property-files.test.tsx` replaces only the two upload calls with JSON describing the file. Everything around them (checks, queueing, order, screens, the fake API) runs as in the app; the multipart request itself was checked against the real API in the browser.

Coverage is measured with v8 (`npm run coverage`, report in `coverage/index.html`). It stands at about 97% of statements, 91% of branches and 98% of lines, and the config fails the run below 95 / 88 / 96 so a new screen cannot arrive untested. The shadcn components, the generated route tree and API types, `main.tsx` and the test helpers are left out of the count. What stays uncovered is mostly defensive branches that the fake API cannot reach (a missing element, an upload hook's failure path).
